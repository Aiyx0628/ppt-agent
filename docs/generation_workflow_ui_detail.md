# DeckFlow 生成流程与页面实现细节

更新日期：2026-04-09

## 1. 目标

本文基于当前最新共识，明确 DeckFlow 的真实产品流程、页面结构和实现细节，作为后续开发的直接依据。

这份文档解决三个问题：

1. 用户真正的输入是什么。
2. `搜索 / 初稿 / 设计稿` 三个阶段分别代表什么。
3. 前端两页结构和后端数据流如何一一对应。

## 2. 正确的业务主流程

系统主流程必须固定为：

1. 用户上传一份文本资料
2. 用户输入需求、风格、页数等约束
3. 系统基于资料内容 + 用户需求 + 外部搜索 / 知识来源生成 `research_pack`
4. 系统基于 `brief + research_pack` 生成整套 `outline`
5. 前端进入 `搜索` 视图，逐页展示“这页应该写什么”，核心是搜索结果、事实、摘要和引用来源
6. 系统基于每页搜索结果和总结生成单页策划与初稿
7. 系统基于初稿进一步生成 `设计稿`

其中：

- `搜索` 不是普通全文检索页，而是“逐页内容研究结果页”
- `初稿` 才是第一次真正看到 PPT 内容成稿
- `设计稿` 是对初稿进行视觉强化和版式精修后的结果

## 3. 用户输入模型

### 3.1 必填输入

用户在第一页必须完成两类输入：

- 文件输入
- 文本需求输入

### 3.2 文件输入

首版至少支持：

- `.md`
- `.txt`
- `.docx`

首版处理策略：

- 前端只负责上传文件
- 后端负责解析文本内容
- 后端统一提取为纯文本正文，作为 research 和 outline 的上游输入

建议数据结构：

```json
{
  "file_id": "file_xxx",
  "filename": "deck_source.docx",
  "file_type": "docx",
  "content_text": "...extracted plain text..."
}
```

### 3.3 需求输入

第一页中央提供结构化输入项：

- 主题
- 使用场景
- 受众
- 风格
- 页数
- 是否联网搜索
- 是否启用知识库

同时允许用户在底部对话框中补充自然语言要求，例如：

- “重点突出产品价值，不要太学术”
- “适合给老板汇报，风格偏简洁科技”
- “控制在 12 页以内”

## 4. 后端阶段定义

## 阶段 A：Source Intake

输入：

- 用户上传文件
- 用户填写需求

输出：

- `source_document`
- `project`
- `project_config`

后端职责：

- 解析文件内容
- 保存原文件和提取后的文本
- 建立项目主记录

## 阶段 B：Brief + Research

输入：

- 文档正文
- 用户需求
- 外部搜索结果 / 知识库结果

输出：

- `requirement_brief`
- `research_pack`

这里的 `research_pack` 必须是结构化结果，而不是一段自由文本。

建议结构：

```json
{
  "project_id": "proj_001",
  "version": 1,
  "page_candidates": [
    {
      "page_key": "p1",
      "topic": "行业背景",
      "facts": ["..."],
      "summary": "...",
      "clusters": ["市场趋势", "用户痛点"],
      "citations": [
        {
          "title": "...",
          "url": "https://...",
          "snippet": "..."
        }
      ]
    }
  ]
}
```

关键要求：

- 必须包含事实
- 必须包含摘要
- 必须包含主题聚类
- 必须包含引用来源
- 引用来源必须可点击

## 阶段 C：Outline Generation + Editing

输入：

- `requirement_brief`
- `research_pack`

输出：

- `outline`

前端能力：

- 调整顺序
- 改标题
- 删除页面
- 新增页面

说明：

- 这里产出的不是 PPT 页面，而是“整套 PPT 的叙事骨架”
- 这是从内容研究进入页面生产的中间桥梁

## 阶段 D：Search View

输入：

- `outline`
- `research_pack`

输出：

- 每一页对应的搜索研究展示

这一阶段的页面含义必须明确：

- 左侧：PPT 页面占位框
- 中间：当前页对应的 research 结果
- 展示内容：事实、摘要、来源 URL、引用片段、主题聚类

这一步的目标不是展示成品页面，而是告诉用户：

- 这页的内容来源于什么
- 这页为什么这样组织
- 这页有哪些可信事实支撑

## 阶段 E：Draft Generation

输入：

- 当前页 `outline`
- 当前页 research facts / summary / citations

输出：

- `slide_plan`
- `draft_slide`

这里的“初稿”定义为：

- 已经是一页真正的 PPT 内容稿
- 用户在右侧可以看到完整 PPT
- 用户可以编辑文案、块顺序、重点句子

首版建议：

- 初稿先以结构化 JSON + HTML/SVG 预览方式渲染
- 前端右侧必须使用“PPT 加载器 / 画布预览器”形式，而不是只显示卡片列表

## 阶段 F：Design Generation

输入：

- `draft_slide`

输出：

- `design_slide`

设计稿定义：

- 在初稿基础上进行视觉强化
- 强化字体层级、留白、配色、图形元素和布局精度
- 最终用于导出或高质量预览

说明：

- `初稿` 解决“写什么、怎么组织”
- `设计稿` 解决“怎么更专业、更像成品”

## 5. 前端页面结构

前端只分成两个页面。

## 页面 1：输入页

这是系统入口页。

页面结构：

- 中央区域：主题、风格、页数、场景等快捷按钮和输入组件
- 底部固定对话框：支持上传文件、发送文本、补充要求

布局要求：

- 中央是结构化配置区
- 底部对话框是持续可用的自然语言入口
- 页面视觉要明显表达“先输入资料和要求，再开始生成”

组件建议：

- 文件上传区
- 需求输入区
- 风格选择器
- 页数选择器
- 联网开关
- 底部消息框
- 开始生成按钮

## 页面 2：生成页

这是核心工作台页面。

页面分区：

- 左上方：三个阶段按钮
- 左侧：PPT 页面占位框 / 缩略图导航
- 中间：阶段主内容区
- 右侧：完整 PPT 预览区或设计稿预览区

### 5.1 左上方阶段按钮

固定为：

- `搜索`
- `初稿`
- `设计稿`

要求：

- 默认自动进入 `搜索`
- `搜索` 完成后自动进入 `初稿`
- 用户可以手动切换查看
- `设计稿` 在未生成前显示加载或禁用状态

### 5.2 左侧页面占位框

左侧列表代表整套 PPT 的页面导航。

搜索阶段：

- 左侧显示每个 PPT 页面占位框
- 未完成时显示骨架加载态
- 完成后显示页标题和状态

初稿阶段：

- 左侧显示真实页缩略图
- 当前选中页高亮

设计稿阶段：

- 左侧继续显示页缩略图
- 可用于切换当前设计稿页

### 5.3 中间主区域

#### 搜索阶段

中间显示：

- 当前页主题
- 研究摘要
- 事实列表
- 主题聚类
- 引用来源
- 可点击 URL

这是一个“研究面板”，不是 PPT 页面。

#### 初稿阶段

中间显示：

- 当前页的内容结构
- 当前页的标题、重点句、模块块
- 用户可以编辑文本

右侧显示：

- 完整 PPT 预览器
- 当前页在预览器中高亮

#### 设计稿阶段

中间或右侧主视觉区域显示：

- 完整设计稿画布
- 当前页设计稿
- 更接近最终导出效果

## 6. 关键交互细节

### 6.1 自动推进规则

- 提交输入后自动进入生成页
- 默认进入 `搜索`
- `research_pack` 对应内容生成完毕后自动切到 `初稿`
- 用户点击 `设计稿` 时触发设计稿生成或查看设计稿结果

### 6.2 PPT 加载器要求

右侧的 PPT 预览器必须满足：

- 切页顺滑
- 滚动顺滑
- 当前页高亮明显
- 切换不闪烁
- 支持骨架屏

不能做成：

- 简单图片列表
- 生硬刷新
- 每次切页全区域闪白

### 6.3 编辑能力

初稿阶段至少支持：

- 改标题
- 改重点句
- 改块顺序
- 调整当前页内容

设计稿阶段首版可先弱编辑，但至少支持：

- 查看
- 切页
- 重新生成当前页

## 7. 前后端契约建议

## 7.1 输入页接口

- `POST /api/projects`
- `POST /api/projects/{id}/sources/upload`

## 7.2 Search 阶段接口

- `POST /api/projects/{id}/research/run`
- `GET /api/projects/{id}/research`

## 7.3 Outline 阶段接口

- `POST /api/projects/{id}/outline/generate`
- `GET /api/projects/{id}/outline`
- `PATCH /api/projects/{id}/outline`
- `POST /api/projects/{id}/outline/reorder`

## 7.4 Draft 阶段接口

- `POST /api/projects/{id}/slides/{slideId}/draft/generate`
- `GET /api/projects/{id}/slides/{slideId}/draft`
- `PATCH /api/projects/{id}/slides/{slideId}/draft`

## 7.5 Design 阶段接口

- `POST /api/projects/{id}/slides/{slideId}/design/generate`
- `GET /api/projects/{id}/slides/{slideId}/design`

## 8. 当前开发顺序

按当前最新方向，接下来的实现顺序应固定为：

1. 输入页重构
2. 文件上传与文本解析
3. `research_pack` 结构化生成
4. Outline 生成与编辑
5. 生成页重构为 `搜索 / 初稿 / 设计稿`
6. 初稿单页生成与右侧 PPT 预览器
7. 设计稿单页生成

## 9. 完成标准

完成后应满足以下判断标准：

- 用户可以上传资料并输入需求
- 系统可以先显示 research 结果，而不是直接跳成 PPT
- 用户可以看到整套 PPT 的 outline 并调整
- 初稿阶段右侧是完整 PPT 预览器
- 设计稿阶段是基于初稿进一步精修的结果
- 页面结构一眼能看出自己处于 `搜索 / 初稿 / 设计稿` 哪个阶段
